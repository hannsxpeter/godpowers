# Architecture Delta: Authorized AI Provenance Cleaning

## Scope of This Delta

- [DECISION] This delta adds one first-party extension boundary and does not change the Godpowers core runtime, state schema, command families, or default installation profile.
- [DECISION] The extension contains a command skill and a specialist contract, while the selected `watermarks-remover` deployment owns all deterministic inspection and cleaning logic.

## Options Considered

| Option | Assessment | Decision |
|---|---|---|
| Vendor the upstream Python service into the Godpowers package | [DECISION] This would add a second runtime, optional native tools, model backends, and supply-chain ownership to the dependency-light core. | [DECISION] Rejected. |
| Add a core `/god-remove-ai-marks` command | [DECISION] This would expand a frozen public command surface for an optional domain capability. | [DECISION] Rejected. |
| Ship an extension that calls the upstream HTTP contract | [DECISION] This preserves lazy activation, keeps the service user-operated, and reuses the upstream implementation named by the user. | [DECISION] Selected. |

## Critical Flow

1. [DECISION] The skill resolves the input and output paths without changing either file.
2. [DECISION] The specialist confirms that the request establishes ownership or processing authorization, and asks for confirmation only when that fact is absent.
3. [DECISION] The specialist parses `WATERMARKS_SERVICE_URL`, rejects embedded credentials, and accepts only loopback HTTP or HTTPS endpoints by default.
4. [DECISION] For a non-loopback HTTPS endpoint, the specialist displays the destination and retention uncertainty, then waits for explicit upload consent before reading the source into a request payload.
5. [DECISION] The specialist reads an optional bearer token from `WATERMARKS_SERVICE_API_KEY` without printing, persisting, or placing it in a process argument.
6. [DECISION] The specialist invokes the bundled client, which calls `/health`, `/capabilities`, and `/openapi.json` with bounded request and response limits before any content upload.
7. [DECISION] The client reads the input through no-follow identity checks, holds request and response bodies in memory, and calls `/inspect` before any clean request.
8. [DECISION] The specialist compares requested options with reported capabilities and stops before `/clean` when an explicit pixel backend is unavailable.
9. [DECISION] The client calls `/clean` once, validates bounded JSON plus strict canonical base64, and decodes only an output that stays within the input-relative size limit.
10. [DECISION] The client verifies an allowlisted extension, service-kind agreement, and format-appropriate bytes, revalidates the pre-upload parent and destination identities, writes an exclusive mode-0600 sibling file, and atomically publishes it without clobbering a new or changed path.
11. [DECISION] When in-place cleaning was explicitly requested, the specialist first preserves a recoverable sibling backup and only then performs the atomic replacement.
12. [DECISION] The specialist optionally performs an approved prose rewrite, sends the rewritten text through the deterministic clean flow again, and keeps the pre-rewrite cleaned file recoverable.
13. [DECISION] The client keeps request and response bodies in memory, removes active output temporary files on success or handled failure, and returns separate deterministic, best-effort, and residual-risk sections.

## Trust Boundaries

- [DECISION] Filesystem boundary: the specialist may read only the user-selected input and may write only the selected output, a recoverable backup for explicit in-place work, guarded-replacement recovery data when needed, and permission-restricted temporary files under a pinned parent identity.
- [DECISION] Service boundary: every non-loopback upload is an external data transfer, requires destination-specific consent, rejects redirects and mixed loopback or non-loopback DNS sets, and pins one classified address set for the active invocation.
- [DECISION] Credential boundary: `WATERMARKS_SERVICE_API_KEY` remains process environment input and is never copied into request JSON, logs, command arguments, Godpowers state, or artifacts.
- [DECISION] Response boundary: HTTP success alone is untrusted until the JSON shape and cleaned payload validate locally.
- [DECISION] Capability boundary: `/capabilities` is runtime evidence for optional tools and backends, not evidence that a vendor detector will accept the result.

## Failure and Degradation

| Dependency or step | Timeout and retry stance | User-visible behavior |
|---|---|---|
| Service health | [DECISION] Use a 5-second connection timeout and a 15-second total timeout, with no cross-surface fallback. | [DECISION] Report the service as unreachable, show upstream startup options, and write nothing. |
| Deterministic inspect or clean | [DECISION] Use a 120-second total timeout and do not retry an interrupted clean automatically. | [DECISION] Preserve the source and final output, delete handled temporary files, and report that completion is unknown. |
| Pixel regeneration | [DECISION] Use a separately disclosed longer timeout selected for the configured backend and never start without explicit approval. | [DECISION] Report unavailable or timed-out backend work without claiming pixel watermark removal. |
| Invalid, oversized, or incomplete response | [DECISION] Enforce HTTP byte limits, bounded report structure, canonical base64, an input-relative decoded limit, and no retry. | [DECISION] Keep the source unchanged and report a fixed response-contract failure without including content or credentials. |
| Local atomic publication | [DECISION] Pin parent and destination identities before upload, use no-clobber hard-link publication for an absent destination, and move an approved existing path through a guarded recovery name before no-clobber publication. | [DECISION] Reject parent swaps and concurrent destination changes, restore the prior path when possible, and report any retained recovery path. |
| Cleanup interruption | [HYPOTHESIS] A process kill can bypass normal cleanup even with signal handlers. | [DECISION] Use permission-restricted, uniquely named temporary files and sweep only exact generated names owned by the current user with private mode bits. |

## Capacity Envelope

- [DECISION] One command invocation processes one file at a time and accepts at most 64 MiB so client memory and service work do not multiply across an unbounded batch.
- [DECISION] Base64 expands input bytes by approximately four thirds before JSON overhead, so the specialist checks available local storage before creating request and response payloads for large inputs.
- [DECISION] The upstream service remains authoritative for its configured input limit, and a service rejection produces no local output mutation.
- [HYPOTHESIS] Directory audits can remain sequential until measured adoption shows that parallel inspection is necessary and safe for the selected service.

## Architecture Decision Records

### ADR-004: Keep provenance cleaning in a lazy extension

- [DECISION] Context: the capability is useful but optional, relies on a separate service, and does not belong in every Godpowers project run.
- [DECISION] Decision: ship `@godpowers/provenance-pack` with `/god-remove-ai-marks` and a dedicated specialist.
- [DECISION] Rationale: an extension preserves the frozen core command surface, avoids new production dependencies, and matches the existing lazy pack contract better than vendoring or a core command.
- [DECISION] Flip point: move the command into core only if provenance cleaning becomes a required gate for most Godpowers workflows and can run without adding a second runtime or silent external data path.
- [DECISION] Consequence: users install the pack and operate the upstream service separately.

### ADR-005: Reuse the upstream HTTP contract through a deterministic client

- [DECISION] Context: the user selected an upstream project whose skill is already a thin client for a service-owned cleaning engine.
- [DECISION] Decision: ship a dependency-free Node.js client that validates `/health`, `/capabilities`, `/openapi.json`, `/inspect`, and `/clean` while leaving every cleaning algorithm in the upstream service.
- [DECISION] Rationale: deterministic validation closes redirect, DNS, response, and filesystem gaps that prose-only agent instructions cannot enforce, while direct contract reuse still avoids algorithm drift.
- [DECISION] Flip point: replace the bundled client only when the upstream publishes a dependency-equivalent signed client with the same network, response, and file-safety guarantees.
- [DECISION] Consequence: service outages degrade the extension completely but do not affect Godpowers core operation.

### ADR-006: Require visible consent for remote content transfer

- [DECISION] Context: source files can contain personal, confidential, or proprietary data even when the integration itself stores no identity fields.
- [DECISION] Decision: loopback is the default, non-loopback endpoints require HTTPS plus explicit destination-specific consent, and remote retention remains disclosed as unknown unless the user supplies policy evidence.
- [DECISION] Rationale: this makes the new external data path visible and keeps authorization with the user.
- [DECISION] Flip point: replace per-invocation consent only when a future integrations pillar defines a durable, inspectable destination grant with revocation and retention metadata.
- [DECISION] Consequence: remote service use has one deliberate confirmation step before upload.
