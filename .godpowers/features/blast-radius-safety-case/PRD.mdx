# Feature PRD: Blast Radius Safety Case

## Feature Context

- [DECISION] This feature extends the global product requirement namespace after shipped requirement `P-MUST-35`, so its requirements use stable IDs `P-MUST-36` through `P-MUST-43` and must never be renumbered or reused after release.
- [DECISION] The primary product form remains CLI or SDK because Godpowers distributes through `npx godpowers` and users operate its installed slash-command and specialist contracts inside supported AI coding tools.
- [DECISION] The product archetype is a developer workflow platform, while no industry or regulatory overlay is evidenced for this review-protocol increment.
- [DECISION] The existing Godpowers charter and canonical PRD govern this bounded addition, so the documentation profile does not require a second initiation brief for the blast-radius increment.
- [DECISION] The feature adapts safety-case ideas from the Cursor pstack [`blast-radius` skill](https://github.com/cursor/plugins/blob/main/pstack/skills/blast-radius/SKILL.md) into original Godpowers guidance, test fixtures, and review contracts without copying upstream wording.

## 1. Problem Statement

- [DECISION] A Godpowers quality review can inspect the changed lines, direct callers, and static impact output yet still pass a change whose real failure appears in a pinned dependency implementation, lifecycle transition, serialized contract, installer copy, generated surface, package boundary, or cross-language consumer.
- [DECISION] The current review verdict does not require one load-bearing safety fact, does not distinguish an assertion from an executed proof, and does not separate a confirmed risk from a candidate that was checked and cleared.
- [DECISION] A Godpowers maintainer can therefore receive a confident PASS while the claim that makes the change safe exists only as reviewer prose, and a later installer, package consumer, state reader, or host runtime discovers the missed behavior after commit or publication.
- [HYPOTHESIS] A shared safety-case protocol with one explicit safety fact, a five-level evidence ladder, boundary-aware scanning, and ledger-backed focused probes will reduce high-impact review escapes; validation will use adversarial fixtures and findings from the first two release candidates containing the feature.

## 2. Target Users

- [DECISION] Primary: the Godpowers maintainer or release engineer who reviews Node.js CommonJS changes across runtime helpers, skill contracts, specialist agents, installer targets, generated state, package contents, and Node.js 18, 20, and 22 before committing or publishing `godpowers`.
- [DECISION] Secondary: a `god-quality-reviewer` or `/god-review` operator working in fresh context who must turn a diff, relevant Pillars, static impact candidates, and verification evidence into a defensible PASS or FAIL without claiming that grep output proves behavior.
- [DECISION] Beneficiary: a solo founder or engineering team of 1 to 5 people using Godpowers in Claude Code, Codex, Cursor, Windsurf, Gemini, or another supported host who relies on review to catch failures beyond the edited repository lines before the slice is committed.

## 4. Functional Requirements

### MUST

- P-MUST-36 [DECISION] Godpowers must define one shared blast-radius safety-case protocol in `references/building/BLAST-RADIUS.md` and make the existing `/god-review` flow and `god-quality-reviewer` consume it without adding a public command.
  - [DECISION] Acceptance: the shared protocol defines required inputs, boundary scan, evidence ladder, impact policy, proof rules, output sections, pass criteria, and exact remediation behavior in one source referenced by both review contracts.
  - [DECISION] Acceptance: `/god-review` keeps its existing public name and two-stage sequence, while Stage 2 cannot PASS until its blast-radius safety case satisfies the shared protocol.
  - [DECISION] Acceptance: a repository-surface test fails if the shared protocol is absent, either review consumer loses its reference, or a new slash command, route, recipe, workflow, or specialist is introduced for this feature.

- P-MUST-37 [DECISION] Every blast-radius safety case must name exactly one load-bearing safety fact and grade its strongest evidence on a five-level ladder.
  - [DECISION] Acceptance: level 1 is an unsupported reviewer assertion, level 2 is a specific source citation, level 3 refutes a named failure path through traced branches or consumers, level 4 is a focused executed probe, and level 5 is a runtime reproduction through the applicable running or installed delivery boundary.
  - [DECISION] Acceptance: the safety fact states the concrete condition that must remain true for the reviewed change to be safe, the affected boundary, the consequence if false, the evidence level, and the evidence citation.
  - [DECISION] Acceptance: every level 1, 2, or 3 conclusion is labeled `UNPROVEN`, and a reviewer cannot combine several lower-level items to claim level 4 or 5 evidence.

- P-MUST-38 [DECISION] The protocol must classify review conclusions by proof state and impact, then enforce different verdict behavior for high-impact and lower-impact `UNPROVEN` claims.
  - [DECISION] Acceptance: the review output contains separate Confirmed Risks, Cleared Risks, and Unproven Claims sections, and each entry names likelihood, impact, location or boundary, evidence level, evidence citation, and verification method.
  - [DECISION] Acceptance: Confirmed Risks contain level 4 or 5 evidence that the failure exists, Cleared Risks contain level 4 or 5 evidence that the named failure path is safe, and every conclusion supported only by levels 1 through 3 appears under Unproven Claims.
  - [DECISION] Acceptance: an `UNPROVEN` claim is high impact when failure could compromise authentication or authorization, disclose secrets, corrupt or lose state, execute a destructive action, break the installer or published package, violate a public or serialized contract, or invalidate verification-ledger integrity.
  - [DECISION] Acceptance: any high-impact `UNPROVEN` claim makes Stage 2 FAIL, while a lower-impact `UNPROVEN` claim produces a warning that names one exact command, fixture, dependency trace, or runtime reproduction needed to clear or confirm it.

- P-MUST-39 [DECISION] Every blast-radius review must scan beyond text matches and direct imports across 10 named boundary classes before it grades the safety fact.
  - [DECISION] Acceptance: the boundary inventory records the dependency implementation, pinned dependency version, local dependency patches, lifecycle or ordering timing, serialized or public API contracts, database or disk-state fields, configuration or feature flags, generated or installed surfaces, npm package surfaces, and cross-language consumers.
  - [DECISION] Acceptance: each boundary row cites the repository path, lockfile entry, installed dependency source, generated target, package manifest, schema, consumer, or exact search that supports the result, or records a not-applicable reason tied to an observed repository fact.
  - [DECISION] Acceptance: fixtures include a risk visible only in pinned dependency code, a lifecycle-ordering regression, a serialized field consumer, an installed copy drift, a missing package file, and a cross-language invocation so direct-caller review alone cannot pass the suite.

- P-MUST-40 [DECISION] Focused probes and runtime reproductions must use the existing `npx godpowers verify` path so the review cites durable claim records instead of terminal narration.
  - [DECISION] Acceptance: every level 4 or 5 item cites a `.godpowers/ledger/verifications.jsonl` executed record containing the same safety claim, exact command, canonical substep, successful exit code, timestamp, and `verified: true` verdict.
  - [DECISION] Acceptance: a failed, timed-out, attested-only, mismatched, or pre-change record cannot clear a risk, and the review names the exact fresh `npx godpowers verify "<focused probe>" --substep=<id> --claim="<safety fact>" --project=.` invocation needed next.
  - [DECISION] Acceptance: the feature uses the existing verification ledger, state rollup, and hash-chained gate event behavior without creating a second evidence store or changing `verify` into a new public operation.

- P-MUST-41 [DECISION] Runtime reproduction must be required only when the named failure depends on real lifecycle, installation, packaging, process, browser, service, or host behavior and an evidenced runnable target exists.
  - [DECISION] Acceptance: a reviewer records level 5 as not applicable when the safety fact is completely decided by deterministic local transformation or static contract evidence, and the reason names why runtime state cannot change the conclusion.
  - [DECISION] Acceptance: a reviewer cannot demand level 5 when no runnable target, fixture, or faithful substitute exists, and instead records the missing target under Unproven Claims with owner, impact, and exact evidence needed.
  - [DECISION] Acceptance: when runtime behavior is applicable and a runnable target exists, static success or a level 4 unit probe cannot clear the runtime-specific failure path until the existing runtime, installed-package, or consumer fixture is executed through `godpowers verify`.

- P-MUST-42 [DECISION] Godpowers must add an independent blast-radius reviewer only for wide changes, while keeping the existing two-stage review sufficient for bounded changes.
  - [DECISION] Acceptance: a change is wide when it crosses at least 3 of the 10 required boundary classes or touches at least 2 high-impact classes from the impact policy, and the review records the matched classes before another reviewer is spawned.
  - [DECISION] Acceptance: a wide change receives at least 2 independent blast-radius safety cases in fresh contexts, and the final Stage 2 verdict reconciles differences in safety fact, boundary inventory, evidence grade, and risk classification without treating reviewer agreement as proof.
  - [DECISION] Acceptance: a bounded change records the threshold calculation and uses the normal Stage 2 reviewer, so multi-review work does not become a mandatory cost for every documentation edit or local refactor.

- P-MUST-43 [DECISION] Static impact output must remain a candidate generator, and the shipped feature must preserve independent authorship, package discipline, and the existing public surface.
  - [DECISION] Acceptance: results from `lib/impact.js`, grep, AST search, LSP references, or import graphs appear only as boundary candidates until source tracing, an executed probe, or runtime reproduction proves the behavioral claim.
  - [DECISION] Acceptance: `INSPIRATION.md` links the upstream pstack `blast-radius` skill, records the safety-case concepts adapted, states that Godpowers authored its protocol and fixtures independently, and does not imply that pstack code ships in the npm package.
  - [DECISION] Acceptance: the implementation copies no upstream prose or code; if a future change distributes a copy or substantial portion, that change must retain the upstream copyright and MIT permission notice before release.
  - [DECISION] Acceptance: validation documentation, `CHANGELOG.md`, and `RELEASE.md` explain the evidence ladder, verdict policy, conditional wide-change review, and candidate-versus-proof boundary, while package checks confirm 0 new production dependencies and 0 new commands before publication.

### SHOULD

- [DECISION] This feature has no SHOULD requirements because omitting any named safety-case, proof, enforcement, boundary, provenance, or release behavior would make a PASS verdict ambiguous.

### COULD

- [DECISION] This feature has no COULD requirements because new analysis commands, hosted review services, configurable evidence ladders, and generalized static-analysis engines are outside the bounded increment.

## Scope and No-Gos

### In Scope

- [DECISION] One shared blast-radius reference consumed by the existing `/god-review` flow and `god-quality-reviewer` contract.
- [DECISION] One load-bearing safety fact, the five-level evidence ladder, impact classification, and Confirmed Risks, Cleared Risks, and Unproven Claims output sections.
- [DECISION] Beyond-grep review across dependency, lifecycle, contract, state, configuration, generation, installation, package, and cross-language boundaries.
- [DECISION] Focused executed probes and applicable runtime reproductions backed by existing `godpowers verify` claim records.
- [DECISION] Conditional independent multi-review for changes that meet the explicit wide-change threshold.
- [DECISION] Focused fixtures, test-runner integration, package checks, validation documentation, upstream acknowledgement, changelog, release notes, and existing release gates.

### Explicitly Not In Scope

- [DECISION] This feature will not add `/god-blast-radius`, another slash command, a new CLI command, a route, a recipe, a workflow, or a specialist type.
- [DECISION] This feature will not add pstack, a static-analysis framework, a model SDK, a hosted review service, or any npm production dependency.
- [DECISION] This feature will not treat grep, direct imports, `lib/impact.js`, AST search, LSP references, reviewer consensus, or a source citation as executed proof.
- [DECISION] This feature will not require runtime reproduction when the named failure is not runtime-dependent or no evidenced runnable target exists.
- [DECISION] This feature will not copy or lightly rewrite upstream pstack prose, code, fixtures, examples, or result formats.
- [DECISION] This feature will not weaken the existing Stage 1 specification gate, Stage 2 quality dimensions, verification ledger, release checks, or human approval boundary for publication.
- [DECISION] This feature will not make lower-impact uncertainty disappear; it remains a visible warning with the exact next proof needed.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| [HYPOTHESIS] Reviewers could turn the boundary inventory into a checklist that records searches without testing the one fact that makes the change safe. | [DECISION] Require one load-bearing safety fact, grade its strongest evidence, and treat every static result as a candidate rather than proof. |
| [HYPOTHESIS] Strict evidence levels could cause reviewers to run broad slow suites that do not isolate the failure path. | [DECISION] Require a focused probe tied to the safety claim, retain exact ledger evidence, and reserve runtime reproduction for applicable behavior. |
| [HYPOTHESIS] Conditional multi-review could consume extra context without adding independent evidence. | [DECISION] Use a mechanical wide-change threshold, require fresh contexts, reconcile divergent claims, and prohibit reviewer agreement from raising an evidence level. |
| [HYPOTHESIS] Upstream acknowledgement could drift into copied wording or an implied runtime relationship with pstack. | [DECISION] Record concepts only, author Godpowers-native contracts and fixtures, preserve MIT notices if future copying occurs, and verify no pstack package enters production dependencies. |
