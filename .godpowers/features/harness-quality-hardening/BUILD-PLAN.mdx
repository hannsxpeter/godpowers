# Build Plan: Harness Quality Hardening

## Scale And Approval

- [DECISION] Scale: large, because the feature changes verification, specialist dispatch, build gates, slice closeout, quality review evidence, package fixtures, and release behavior.
- [DECISION] Approval: the user explicitly authorized implementation, documentation, release, merge, and npm publication in the current request.
- [DECISION] Approval authority: the orchestrator records that user decision as a hash-bound `user.resolve` event before final plan validation; this plan cannot approve itself.
- [DECISION] Program-design review status: approved for the contracts recorded below.

## Program Design

### File Tree Delta

- [DECISION] Add `lib/program-design.js`, `lib/slice-handoff.js`, `lib/maintainability-trajectory.js`, and `lib/evolution-benchmark.js` as dependency-free CommonJS modules.
- [DECISION] Add focused behavioral tests under `scripts/`, a six-checkpoint fixture under `fixtures/evolution/`, and package-content assertions for the shipped runtime and fixture.
- [DECISION] Modify `scripts/run-tests.js`, `lib/context-budget.js`, `lib/events.js`, `schema/events.v1.json`, `lib/gate.js`, `lib/style-stats.js`, specialist contracts, and the orchestrator runbook.
- [DECISION] Update feature artifacts, product artifacts, public documentation, release documentation, and version surfaces only after runtime verification passes.

### Module Boundaries

- [DECISION] `scripts/run-tests.js` owns child-process execution and terminal presentation but no workflow state.
- [DECISION] `lib/context-budget.js` owns declaration parsing, source resolution, byte estimation, deterministic loadout planning, and a spawn-blocking verdict.
- [DECISION] `lib/program-design.js` owns plan parsing and validation, while `lib/gate.js` owns whether its findings block Build.
- [DECISION] `lib/slice-handoff.js` owns a bounded projection and cannot write or reinterpret authoritative state.
- [DECISION] `lib/maintainability-trajectory.js` owns deterministic measurements and signed deltas, while the quality reviewer owns interpretation.
- [DECISION] `lib/evolution-benchmark.js` owns checkpoint reveal order and evidence aggregation but does not call a model or mutate the real project.

### Public Contracts

- [DECISION] Verification exposes `parseOptions`, `runCommands`, and `renderAgentSummary` for behavioral testing while preserving direct CLI use.
- [DECISION] Context budgeting exposes `parseAgentBudget`, `resolveSources`, `plan`, and `planForAgent`, with pinned file bytes, missing required sources, and required overflow represented before spawn.
- [DECISION] Program design exposes `validateText(text, opts)` and `validateFile(file, opts)` returning checks, findings, scale, approval, and verdict.
- [DECISION] Slice handoff exposes `derive(input)`, `serialize(handoff)`, and `write(projectRoot, runId, sliceId, handoff)`.
- [DECISION] Maintainability exposes `snapshot(projectRoot, opts)`, `diff(before, after)`, and `render(report)`.
- [DECISION] Evolution benchmarking exposes `loadScenario`, `createRun`, `recordCheckpoint`, `summarize`, and `render`.

### Call And Data Flow

1. [DECISION] Orchestration resolves a specialist declaration and actual inline payloads through context budgeting before spawn.
2. [DECISION] Planning produces a size and either a complete approved program design or a small-change skip rationale.
3. [DECISION] The build gate validates that plan before accepting Build closure evidence.
4. [DECISION] The executor records a maintainability baseline, implements one slice, verifies behavior, and records the post-slice delta.
5. [DECISION] Slice closeout projects plan, state, event, linkage, and verification evidence into one bounded handoff.
6. [DECISION] The independent reviewer consumes the code diff, verification evidence, and maintainability trajectory.
7. [DECISION] The evolution benchmark repeats the same evidence shape across six isolated checkpoint reveals.

### Caller Usage

- [DECISION] The build gate and specialist contracts call one focused CommonJS helper per validation or evidence boundary and consume stable plain-object results.
- [DECISION] Cold-context specialists receive exact helper names, artifact paths, and verdict fields in the approved plan instead of inferring integration behavior.

### Interface Burden

- [DECISION] Each helper accepts only the project-local text, paths, or normalized records its direct callers already possess.
- [DECISION] No helper adds provider configuration, model selection, network credentials, or another authoritative state shape.

### Seam Justification

- [DECISION] Dependency-free runtime validators are the seam because prose specialists need deterministic release gates without introducing a service or parser dependency.
- [DECISION] Structured handoffs are the process seam because sessions can end between slices while current state remains authoritative.

### Alternative Shapes

- [DECISION] Alternative A: keep every contract in specialist prose, which cannot provide deterministic gate evidence or fresh-process resume proof.
- [DECISION] Alternative B: introduce a workflow service and database, which breaks the local, offline, inspectable Godpowers runtime model.
- [DECISION] Selected shape: add bounded CommonJS validators and projections beside the existing gate, event, and specialist contracts.

### Deviation Return Rule

- [DECISION] If the same plan deviation occurs twice, stop production edits and return to planning before changing the approved code shape.

### Reused Patterns

- [DECISION] Reuse `lib/frontmatter.js` for specialist and plan metadata, `lib/events.js` for bounded evidence vocabulary, `lib/atomic-write.js` for durable writes, and `scripts/test-harness.js` for behavioral tests.
- [DECISION] Reuse `lib/style-stats.js` exclusions and sample-count discipline instead of introducing parser dependencies.
- [DECISION] Reuse the existing build gate, fresh-context executor, specification reviewer, quality reviewer, and release package checks.

### Non-Goals

- [DECISION] Do not add HumanLayer, Fold, Effect, Kubernetes, model calls, network calls, a new MCP tool, a UI, or a second authoritative state store.
- [DECISION] Do not make maintainability values an independent pass or fail threshold during calibration.
- [DECISION] Do not change normal test output unless compact mode is explicitly selected.

### Verification Points

- [DECISION] Every new module receives targeted behavioral coverage and clears the per-file line floor.
- [DECISION] Static checks validate all specialist context contracts and the updated MCP dependency boundary.
- [DECISION] The full test suite, lint, audit, package checks, self-project truth checks, and pre-publication checks must pass before release.
- [DECISION] The release must verify both npm packages and the isolated published installation after the tag workflow completes.
