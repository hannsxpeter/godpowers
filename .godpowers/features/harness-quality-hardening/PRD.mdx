# Feature PRD: Harness Quality Hardening

## Feature Context

- [DECISION] This feature extends the global product requirement namespace after shipped requirement `P-MUST-23`, so its six requirements use stable IDs `P-MUST-24` through `P-MUST-29` and must never be renumbered or reused after release.
- [DECISION] This feature strengthens the existing Godpowers pure-skill runtime, deterministic Node.js helpers, disk-authoritative state, specialist boundaries, vertical-slice build flow, and release gates without introducing a second orchestration framework.
- [DECISION] The six capabilities in this PRD are one quality-hardening increment because each capability reduces the cost of detecting, explaining, or correcting code-quality drift during an agent-led build.

## 1. Problem Statement

- [DECISION] Godpowers maintainers and host agents currently spend scarce context on hundreds of successful test lines while complete failure evidence, context-load decisions, slice transition facts, and maintainability changes are not presented through one compact and deterministic quality contract.
- [DECISION] Godpowers already contains context-budget, checkpoint, style-statistics, dogfood, vertical-slice, and independent-review machinery, but the build path does not yet enforce specialist context manifests, program-design review for larger changes, structured slice handoffs, before-and-after maintainability evidence, or sequential requirement-evolution proof.
- [DECISION] The resulting failure mode is specific to Godpowers: a slice can pass its functional tests and two reviews while consuming avoidable agent context, omitting loadout evidence, forcing the next session to reconstruct decisions, and leaving future maintainability deterioration unmeasured.
- [HYPOTHESIS] Compact verification, explicit context loadouts, earlier program-shape review, deterministic handoffs, trajectory deltas, and a sequential evolution benchmark will reduce repair cycles without weakening Godpowers release evidence; validation will compare the first complete benchmark baseline and the first three release candidates after implementation.

## 2. Target Users

- [DECISION] Primary: the Godpowers maintainer or release engineer who runs the dependency-free Node.js test and release suite, reviews specialist output across more than 40 agent contracts, and must diagnose the first actionable failure without feeding the full passing transcript back into an AI coding host.
- [DECISION] Secondary: solo founders and engineering teams of 1 to 5 people who use Godpowers inside Claude Code, Codex, Cursor, Windsurf, Gemini, or another supported host to deliver multi-slice brownfield changes across sessions while preserving approved design intent and requirement traceability.
- [DECISION] Supporting actor: a Godpowers specialist agent that must receive a bounded task-specific loadout, execute one approved vertical slice, and hand the next context a compact factual record derived from disk rather than conversational memory.

## 4. Functional Requirements

### MUST

- P-MUST-24 [DECISION] Godpowers must provide an explicit agent-oriented verification mode that keeps complete test evidence while emitting compact success and focused failure output.
  - [DECISION] Acceptance: a passing full-suite fixture with at least 100 child checks emits no more than 25 terminal lines and 32 KiB, names the suite status, check count, elapsed time, and complete retained-log path, and returns the same exit status as normal mode.
  - [DECISION] Acceptance: a failing fixture stops at the first failed child, names the exact command, exit status, elapsed time, and retained-log path, emits no more than 200 focused diagnostic lines and 64 KiB, and retains the complete untruncated child output without piping it through `head` or `tail`.
  - [DECISION] Acceptance: normal human-readable test output remains available through the existing commands, so compact mode is opt-in for agents and automation until release evidence justifies changing the default.

- P-MUST-25 [DECISION] Godpowers must activate bounded context contracts for every specialist invoked by a workflow and enforce those contracts before the host spawns the specialist.
  - [DECISION] Acceptance: each workflow-invoked specialist declares required context, optional context, and a positive maximum token estimate, or declares explicitly that it needs no project context, and a static check rejects missing or contradictory declarations.
  - [DECISION] Acceptance: context planning fails before spawn when a required source is missing or required context exceeds the budget, drops optional sources in deterministic priority order when needed, and records required-loaded, optional-loaded, optional-dropped, estimated-token, and maximum-token evidence.
  - [DECISION] Acceptance: two runs over the same fixture, task text, and repository state produce byte-identical ordered loadout manifests, and an optional-context overflow fixture never removes a required source.

- P-MUST-26 [DECISION] Godpowers must require a conditional program-design review before implementing every medium or large change while allowing a small change to skip that review with a recorded sizing rationale.
  - [DECISION] Acceptance: every medium or large build plan records the intended file-tree delta, module boundaries, public type or signature changes, call or data flow, existing patterns to reuse, explicit non-goals, and verification points before an executor can start.
  - [DECISION] Acceptance: human-guided mode requires recorded approval of the program-design record, while `--yolo` records the auto-approval and rationale in the existing YOLO decision ledger before execution.
  - [DECISION] Acceptance: plan validation blocks a medium or large slice with a missing or unapproved program-design record, and accepts a small slice only when its size and skip rationale are both present.

- P-MUST-27 [DECISION] Godpowers must derive a compact structured handoff from authoritative plan, state, event, linkage, and verification evidence whenever a slice completes, pauses, or changes owner.
  - [DECISION] Acceptance: every handoff contains the goal, constraints, requirement IDs, status, completed work, in-progress work, blockers, changed files, verification results, decisions, next action, and critical references, and each field points to authoritative disk evidence where that evidence exists.
  - [DECISION] Acceptance: the serialized handoff remains at or below 8 KiB by referencing complete logs and artifacts instead of embedding them, and truncation never removes requirement IDs, blockers, failed verification, or the next action.
  - [DECISION] Acceptance: a resume fixture reconstructs the next executable action from the handoff plus authoritative state in a fresh process without reading the prior conversation, and the handoff cannot override conflicting authoritative state.

- P-MUST-28 [DECISION] Godpowers must capture maintainability baselines and post-slice trajectory deltas and present them to the independent quality reviewer without making uncalibrated metrics a release gate.
  - [DECISION] Acceptance: each completed slice reports source lines, source-file count, function count, median and p90 function length, comment density, TODO and FIXME marker count, duplicated-block count, dependency-edge count, and dependency-cycle count before and after the slice, with signed deltas and sample counts.
  - [DECISION] Acceptance: the same unchanged fixture produces byte-identical metrics, generated or vendored paths are excluded by one documented rule set, and a fixture with known growth, duplication, and a dependency cycle reports the expected direction for every affected delta.
  - [DECISION] Acceptance: the quality reviewer receives the trajectory report and must discuss material deterioration in its verdict, but metric values remain report-only for the first three release candidates and cannot independently fail a build.

- P-MUST-29 [DECISION] Godpowers must provide an incremental evolution benchmark that reveals requirements one checkpoint at a time and measures whether the same codebase remains correct and changeable.
  - [DECISION] Acceptance: the benchmark contains exactly 6 ordered checkpoints, materializes a clean temporary repository, prevents checkpoint N from reading checkpoint N+1, and runs behavior tests plus maintainability measurement after every checkpoint.
  - [DECISION] Acceptance: each checkpoint records implementation-attempt count, behavior-test result, rework volume, changed-line volume, maintainability deltas, accepted-change outcome, and structured-handoff completeness in machine-readable evidence and a human-readable summary.
  - [DECISION] Acceptance: the benchmark command runs deterministically without network access or model credentials, exits nonzero for a failed checkpoint or incomplete evidence, cleans its temporary repository, and retains the final evidence artifact needed to compare future releases.

### SHOULD

- [DECISION] No SHOULD requirement is included because the user authorized all six named capabilities for the same release increment.

### COULD

- [DECISION] No COULD requirement is included because speculative extensions would weaken the bounded feature contract.

## Scope and No-Gos

### In Scope

- [DECISION] Agent-oriented output for the existing full test runner and the child harness behavior needed to retain complete evidence.
- [DECISION] Specialist context declarations, deterministic budget planning, pre-spawn enforcement, evidence recording, and repository-surface validation.
- [DECISION] Conditional program-design content and approval status inside the existing planning and execution workflow.
- [DECISION] Compact slice handoffs derived from existing authoritative sources and verified through fresh-process resume tests.
- [DECISION] Before-and-after maintainability measures, signed deltas, quality-review consumption, and an initial report-only calibration period.
- [DECISION] One deterministic six-checkpoint incremental evolution fixture, runner, machine-readable evidence, human-readable summary, and release comparison baseline.
- [DECISION] Documentation, package-surface checks, release notes, and linkage updates required to ship these six backward-compatible capabilities in the coordinated release that also carries the MCP v2 and Node 20-plus companion boundary.

### Explicitly Not In Scope

- [DECISION] This feature will not adopt HumanLayer, Fold, Effect, AgentControlPlane, Kubernetes, or another orchestration runtime as a production dependency.
- [DECISION] This feature will not replace `.godpowers/state.json` with event sourcing, rewrite the hash-chained event ledger, or make a handoff artifact authoritative over state.
- [DECISION] This feature will not add a dashboard, visual component, web page, or other UI decision while the project UI pillar remains a stub.
- [DECISION] This feature will not replace Pillars routing with Claude-specific conditional XML or expose a large new MCP tool surface.
- [DECISION] This feature will not make maintainability scores a blocking release threshold during the first three release candidates or collapse multiple measures into one quality score.
- [DECISION] This feature will not run live third-party models in CI, publish benchmark repositories, or use future checkpoint requirements to improve an earlier benchmark result.
- [DECISION] This feature will not remove normal human-readable test output or weaken any existing test, audit, package, security, or release gate.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| [HYPOTHESIS] Compact terminal output could hide the only diagnostic needed to repair a failure. | [DECISION] Retain complete child output, print focused first-failure evidence, name the log path, and test beginning, middle, and end failures. |
| [HYPOTHESIS] A strict context budget could omit a file that carries a hidden requirement or current repository rule. | [DECISION] Treat required context as fail-closed, drop only optional context in deterministic order, record every drop, and statically validate the contract before spawn. |
| [HYPOTHESIS] Program-design review could slow trivial fixes enough that users bypass the workflow. | [DECISION] Gate only medium and large changes and require a visible size plus skip rationale for small changes. |
| [HYPOTHESIS] A compact handoff could become a stale competing truth source. | [DECISION] Derive it from authoritative disk evidence, keep source references, and require state to win every conflict in resume tests. |
| [HYPOTHESIS] Maintainers or agents could optimize code for metric values instead of changeability. | [DECISION] Keep separate raw measures and sample counts, require reviewer interpretation, and prohibit standalone gating during calibration. |
| [HYPOTHESIS] A fixed evolution fixture could become overfit and stop representing real requirement change. | [DECISION] Keep future checkpoints inaccessible, record the baseline rather than a timeless pass claim, and revisit live-agent or additional held-out runs only after reproducibility evidence exists. |
