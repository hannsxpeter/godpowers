# Architecture Delta: Harness Quality Hardening

## Scope

- [DECISION] This delta adds deterministic quality helpers and build gates to the existing dependency-free CommonJS runtime.
- [DECISION] `.godpowers/state.json` remains the workflow authority, while logs, handoffs, maintainability reports, and benchmark reports remain derived evidence.
- [DECISION] The delta introduces no external service, production dependency, UI surface, or replacement orchestration runtime.

## Components

| Stable ID | Component | Ownership |
|---|---|---|
| C-verification-output | [DECISION] Agent-oriented verification runner that buffers child output, emits compact success, focuses first-failure diagnostics, and retains the complete log. | [DECISION] `scripts/run-tests.js` plus its behavioral test. |
| C-context-loadout | [DECISION] Specialist context parser, resolver, budget planner, and pre-spawn validator for file-backed and inline inputs. | [DECISION] `lib/context-budget.js`, specialist frontmatter, static checks, and orchestrator runbook. |
| C-program-design | [DECISION] Conditional program-design parser and validator for small, medium, and large build plans. | [DECISION] `lib/program-design.js`, build gate, planner, executor, and reviewers. |
| C-slice-handoff | [DECISION] Bounded projection of slice plan, authoritative state, events, linkage, and verification records. | [DECISION] `lib/slice-handoff.js` and orchestrator closeout instructions. |
| C-maintainability-trajectory | [DECISION] Deterministic source, function, duplication, dependency, and cycle snapshots plus signed deltas. | [DECISION] `lib/maintainability-trajectory.js`, `lib/style-stats.js`, executor, and quality reviewer. |
| C-evolution-benchmark | [DECISION] Offline six-checkpoint harness that reveals one requirement at a time and records changeability evidence. | [DECISION] `lib/evolution-benchmark.js`, `fixtures/evolution/`, and its test command. |

## Flow 1: Agent-Oriented Verification

1. [DECISION] The caller opts into compact output through an explicit command-line flag or environment signal.
2. [DECISION] C-verification-output captures each child process output without shell truncation and appends the complete bytes to a private temporary log.
3. [DECISION] A passing child contributes one structured result containing command, duration, and extracted test count.
4. [DECISION] The first failing child stops the suite and emits command, exit status, duration, bounded focused diagnostics, and the retained-log path.
5. [DECISION] Normal human-readable output remains unchanged when compact mode is absent.

## Flow 2: Specialist Context Loadout

1. [DECISION] Every specialist keeps its existing ordered `inputs` contract and declares a positive `max-tokens` value.
2. [DECISION] C-context-loadout derives required and optional file-backed sources plus required inline source identifiers from the ordered inputs when explicit context arrays are absent.
3. [DECISION] The orchestrator supplies actual inline payloads at dispatch, and C-context-loadout measures them together with identity-pinned file bytes after rejecting symlinks.
4. [DECISION] Missing required sources or required bytes beyond the cap block the spawn.
5. [DECISION] Optional sources are admitted in declaration order until the cap is reached, and later sources are recorded as dropped.
6. [DECISION] A `context.loadout` event records counts and token estimates without recording source contents.

## Flow 3: Program Design And Execution

1. [DECISION] Every executable build plan records `Scale` as small, medium, or large.
2. [DECISION] A small plan records a sizing rationale and program-design skip rationale.
3. [DECISION] A medium or large plan records file-tree delta, module boundaries, public contracts, call or data flow, reused patterns, non-goals, verification points, and approval evidence.
4. [DECISION] Human-guided approval requires a hash-chained `user.resolve` event bound to the exact plan path, plan SHA-256 digest, and reviewer, while `--yolo` records an auto-approval rationale through the existing YOLO decision surface.
5. [DECISION] The build gate invokes C-program-design and blocks execution evidence from closing when the plan is missing, incomplete, or unapproved.

## Flow 4: Slice Projection And Resume

1. [DECISION] The orchestrator passes C-slice-handoff normalized records from the approved slice plan, current state, event stream, linkage, and verification ledger.
2. [DECISION] C-slice-handoff resolves conflicts in favor of current authoritative state and records the conflicting projection as a warning.
3. [DECISION] The handoff preserves requirement IDs, blockers, failed verification, next action, and critical references before trimming optional completed-work detail.
4. [DECISION] The result is written below the active run directory and stays at or below 8 KiB.
5. [DECISION] A fresh process resumes from state plus the handoff without reading prior conversation history.

## Flow 5: Maintainability Trajectory

1. [DECISION] The executor captures a baseline before production edits and a post-slice snapshot after verification.
2. [DECISION] C-maintainability-trajectory excludes generated, vendored, dependency, coverage, build, and Godpowers state directories through one exported rule set.
3. [DECISION] Each snapshot reports source lines, source files, function count, median and p90 function length, comment density, markers, duplicated blocks, dependency edges, and dependency cycles with sample counts.
4. [DECISION] The delta is a signed field-by-field comparison and is byte-stable after volatile paths and timestamps are removed.
5. [DECISION] The quality reviewer must interpret material deterioration, but the metrics remain report-only during the first three release candidates.

## Flow 6: Incremental Evolution Benchmark

1. [DECISION] C-evolution-benchmark loads one manifest containing exactly six ordered checkpoint descriptors and one baseline project.
2. [DECISION] The runner rejects version-control metadata, materializes a fresh temporary Git project with isolated configuration and empty hook plus template directories, and exposes only the active checkpoint brief.
3. [DECISION] After each checkpoint, the runner records attempts, behavior result, changed-line volume, rework volume, maintainability delta, accepted-change outcome, and handoff completeness.
4. [DECISION] A failed checkpoint or incomplete evidence stops the run with a nonzero result.
5. [DECISION] The temporary project is removed, while normalized machine-readable evidence and a human-readable comparison summary remain under the selected output directory.

## Trust Boundaries And Failure Semantics

- [DECISION] Retained verification logs inherit only bytes already emitted by child commands and never add environment dumps or credentials.
- [DECISION] Every context loadout event path contains normalized identifiers, counts, and sizes, never file or inline contents.
- [DECISION] Handoffs reject paths outside the project and active run roots and cannot mutate state, events, linkage, or verification records.
- [DECISION] Maintainability parsers treat repository text as inert input and never execute imports or manifests.
- [DECISION] The evolution benchmark accepts no network dependency or model credential and cleans temporary projects on pass, failure, and handled interruption.
- [DECISION] Invalid compact-output flags, context manifests, plans, handoffs, snapshots, or checkpoint manifests fail with one bounded diagnostic and no partial authoritative-state mutation.

## Capacity

- [DECISION] Verification supports at least 250 child commands and retains at most one complete run log per invocation.
- [DECISION] Context planning supports at least 60 specialists, 150 workflow references, and 500 resolved sources while capping each source at 4 MiB and project traversal at 5,000 entries and depth 48.
- [DECISION] Handoffs are capped at 8 KiB, with mandatory fields protected from trimming.
- [DECISION] Maintainability scanning reuses the existing per-language file caps, caps traversal at 10,000 entries and depth 48, and reports every truncation.
- [DECISION] The evolution benchmark is fixed at six checkpoints, caps baselines at 64 MiB, 5,000 entries, and depth 48, and performs no parallel mutation.

## ADR-007: Gate Context And Program Shape Before Execution

- [DECISION] Context: prompt prose alone cannot prove that a specialist received bounded relevant context or that a larger plan defines the intended code shape.
- [DECISION] Decision: enforce loadout and program-design contracts mechanically before specialist execution can proceed.
- [DECISION] Consequence: stale required paths and unapproved larger plans block early with focused remediation.
- [DECISION] Flip point: relax only after measured false-block evidence identifies a narrower deterministic rule.

## ADR-008: Treat Handoffs And Metrics As Projections

- [DECISION] Context: compact resume and maintainability evidence improve decisions but can drift if promoted to workflow authority.
- [DECISION] Decision: derive both from existing authorities, preserve source references, and resolve every conflict in favor of current state and executed evidence.
- [DECISION] Consequence: projections may be regenerated or discarded without losing workflow truth.
- [DECISION] Flip point: none is planned because ADR-001 assigns workflow authority to `.godpowers/state.json`.

## Rollout And Compatibility

- [DECISION] Compact verification remains opt-in for this release.
- [DECISION] Context and program-design validation become required for new plans and specialist dispatches after repository manifests are migrated in the same change.
- [DECISION] Existing completed projects remain readable, and missing historical trajectory or handoff evidence is reported as unavailable rather than fabricated.
- [DECISION] The core remains CommonJS, supports Node.js 18 or newer, and adds no production dependency; the separately versioned MCP companion follows its declared Node 20-plus engine boundary.
- [DECISION] Every new runtime module receives behavioral tests and per-file coverage before release.

## Have-Nots Checklist

- [x] [DECISION] State authority remains singular.
- [x] [DECISION] No HumanLayer runtime, Effect runtime, Kubernetes component, UI surface, or production dependency is introduced.
- [x] [DECISION] Every new output has a deterministic owner, bounded size, failure contract, and source-of-truth relationship.
- [x] [DECISION] Maintainability metrics remain report-only during calibration.
- [x] [DECISION] The benchmark reveals exactly one checkpoint at a time and runs without network access.
