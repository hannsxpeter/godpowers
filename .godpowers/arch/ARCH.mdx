# Godpowers System Architecture

## System Context

- [DECISION] A developer invokes Godpowers inside an AI coding host, which loads installed skills and specialist agents from the host-specific runtime directory.
- [DECISION] Godpowers reads and writes project-local Pillars, `.godpowers` state, planning artifacts, source files, and verification evidence.
- [DECISION] GitHub Actions and npm are external release services reached only after explicit user authority and identity-bound release gates.

## Architecture Decision Records

### ADR-001: Keep workflow state on disk

- [DECISION] Context: AI coding sessions end, compact, and move between hosts.
- [DECISION] Decision: `.godpowers/state.json` is authoritative and generated views derive from it.
- [DECISION] Rationale: A new session can verify state without trusting conversation memory.
- [DECISION] Flip point: Replace JSON state only if a portable store offers atomic local reads, offline operation, and deterministic export with lower complexity.
- [DECISION] Consequence: State writers must refresh generated views and checkpoints.

### ADR-002: Keep runtime helpers dependency-light

- [DECISION] Context: The installer targets 15 AI coding runtimes and must work in unfamiliar repositories.
- [DECISION] Decision: Runtime helpers use Node.js built-ins and CommonJS, with no production dependency required by the core package.
- [DECISION] Rationale: The package avoids install-time dependency conflicts inside user projects.
- [DECISION] Flip point: Add a dependency only when a measured compatibility or correctness benefit exceeds package and supply-chain cost.
- [DECISION] Consequence: Parsers and filesystem helpers need focused local tests.

### ADR-003: Separate installed capability from active-session evidence

- [DECISION] Context: An agent file on disk proves installation but not that the current host session can spawn a fresh agent.
- [DECISION] Decision: Full host guarantees require an identified host plus explicit active-session spawn evidence.
- [DECISION] Rationale: The dashboard must never report `full on unknown`.
- [DECISION] Flip point: A host-native capability handshake may replace explicit evidence when it is stable and testable.
- [DECISION] Consequence: Some capable hosts report degraded until the active session confirms spawning.

### ADR-004: Keep authorized provenance cleaning in a lazy extension

- [DECISION] Context: provenance cleaning is optional, relies on a separately operated service, and does not belong in every Godpowers project run.
- [DECISION] Decision: ship `@godpowers/provenance-pack` with `/god-remove-ai-marks` and `god-ai-provenance-cleaner` instead of adding a core command.
- [DECISION] Rationale: the extension preserves the frozen core command surface, avoids root production dependencies, and activates only after explicit installation.
- [DECISION] Flip point: move the command into core only if provenance inspection becomes a required gate for most Godpowers workflows and can run without a second runtime or a silent external data path.
- [DECISION] Consequence: users install the pack and operate the upstream service separately.

### ADR-005: Reuse the upstream HTTP contract through a deterministic client

- [DECISION] Context: the selected upstream project owns the provenance-cleaning algorithms but its service responses, network destinations, and filesystem effects cross trust boundaries.
- [DECISION] Decision: ship a dependency-free Node.js client that validates service compatibility, pins approved addresses, rejects redirects, bounds and sanitizes responses, validates output bytes, and publishes through guarded atomic replacement.
- [DECISION] Rationale: deterministic enforcement closes network, response, and filesystem gaps that a prose-only agent contract cannot close while leaving cleaning algorithms upstream.
- [DECISION] Flip point: replace the bundled client only when the upstream publishes a dependency-equivalent signed client with the same network, response, and file-safety guarantees.
- [DECISION] Consequence: service outages disable the extension but do not affect the Godpowers core runtime.

### ADR-006: Require visible consent for remote content transfer

- [DECISION] Context: authorized source files can still contain personal, confidential, or proprietary data.
- [DECISION] Decision: loopback HTTP is the default; a non-loopback destination requires HTTPS and a grant matching its exact normalized origin, with a separate exact-origin grant for private network addresses.
- [DECISION] Rationale: the user sees and controls each external file transfer while remote retention remains disclosed as unknown unless policy evidence is available.
- [DECISION] Flip point: replace per-invocation consent only when a shared integrations contract provides durable destination grants with revocation and retention metadata.
- [DECISION] Consequence: remote service use has a deliberate confirmation step before source bytes enter a request payload.

### ADR-007: Gate bounded context and program shape before execution

- [DECISION] Context: prompt prose alone cannot prove that a specialist received the required project facts or that a larger implementation has an approved code shape.
- [DECISION] Decision: specialist context declarations validate to pinned bytes, and medium or large program-design approval comes from a hash-chained `user.resolve` event bound to the exact plan path and digest before spawn or Build closeout.
- [DECISION] Rationale: missing inputs, oversized required context, project-external plans, and unapproved code shape fail before implementation evidence can be accepted.
- [DECISION] Flip point: relax a validation rule only after measured false-block evidence identifies a narrower deterministic replacement.
- [DECISION] Consequence: every workflow specialist has a bounded contract, while larger changes carry explicit design and approval evidence.

### ADR-008: Keep handoffs and maintainability measures as derived projections

- [DECISION] Context: compact resume records and code-shape measures help later decisions but can drift if they become a competing workflow authority or an uncalibrated score gate.
- [DECISION] Decision: derive handoffs from current authoritative evidence, resolve conflicts in favor of state, and keep individual maintainability measures report-only for three release candidates.
- [DECISION] Rationale: projections can be regenerated without losing truth, and reviewers retain responsibility for interpreting whether a delta is material.
- [DECISION] Flip point: advisory maintainability thresholds may be considered after three release-candidate datasets, but state authority remains fixed by ADR-001.
- [DECISION] Consequence: slice transitions remain resumable and measurable without promoting one metric or summary to source-of-truth status.

## Critical Flows

### Authorized provenance inspection and cleaning

1. [DECISION] C-provenance-skill establishes authorization and delegates the selected path and mode to C-provenance-specialist without changing the source.
2. [DECISION] C-provenance-specialist invokes C-provenance-client, which validates the service origin, destination grants, resolved address set, service version, OpenAPI shape, and requested capabilities before reading source bytes into a request payload.
3. [DECISION] C-provenance-client pins the input, parent, and destination identities, then asks C-watermarks-remover-service to inspect before it requests cleaning.
4. [DECISION] C-provenance-client bounds and sanitizes the service response, validates canonical base64 plus the output format, and publishes to C-user-filesystem through guarded atomic replacement.
5. [DECISION] C-provenance-specialist reports deterministic removals, optional best-effort work, and unresolved risks separately without echoing service-controlled strings as instructions.

### Harness-quality build flow

1. [DECISION] C-context-loadout validates the chosen specialist's required files, optional files, inline task inputs, token cap, path identity, and pinned bytes before orchestration spawns it.
2. [DECISION] C-program-design validates scale and either a small-change skip rationale or complete code-shape evidence plus hash-bound approval before Build can close.
3. [DECISION] C-verification-runner executes checks in order, stops at the first failure in agent mode, and references complete retained evidence from a bounded summary.
4. [DECISION] C-maintainability-trajectory compares the pre-edit and post-verification snapshots, and the independent quality reviewer interprets every material deterioration.
5. [DECISION] C-slice-handoff writes a bounded projection for resume, with current state winning every conflict.
6. [DECISION] C-evolution-benchmark repeats behavior and maintainability evidence across six isolated checkpoint reveals and retains JSON plus Markdown summaries after temporary cleanup.

## Failure and Degradation

| Dependency or step | Timeout and retry stance | User-visible degraded state |
|---|---|---|
| Service health and contract | [DECISION] Use a 5 second connection deadline and 30 second total deadline, reject redirects, and retry no request; the health and contract reads are idempotent by canonical service origin plus requested version. | [DECISION] Report the service as unreachable or incompatible and write no output. |
| Inspect or clean request | [DECISION] Use one 60 second absolute operation deadline and never retry; inspection is read-only, but cleaning is not assumed idempotent without a service-issued operation key. | [DECISION] Preserve source and destination files and report that completion is unknown. |
| Optional pixel backend | [DECISION] Start only after explicit approval and a matching capability response, with no automatic fallback. | [DECISION] Name the unavailable or timed-out capability without claiming pixel removal. |
| Response validation | [DECISION] Reject malformed, oversized, unsupported, kind-mismatched, or noncanonical data without retry. | [DECISION] Keep all final paths unchanged and return a fixed response-contract failure. |
| Guarded publication | [DECISION] Reject parent or destination identity changes and attempt one local restoration when replacement publication fails. | [DECISION] Preserve the competing file, restore the prior destination when possible, and report any retained recovery path. |
| Context or plan validation | [DECISION] Complete each local validation within a 30 second harness deadline, reject missing, escaped, contradictory, oversized, or negatively approved evidence, and never retry; the read-only validation is idempotent by input-byte digest. | [DECISION] Return bounded findings and leave authoritative state unchanged. |
| Trajectory or benchmark input | [DECISION] Complete each fixture checkpoint within a 30 second behavior deadline, reject incompatible snapshots, malformed manifests, future-checkpoint access, or incomplete evidence, and never retry a mutation; snapshot reads are idempotent by repository-byte digest. | [DECISION] Stop at the first invalid checkpoint, retain partial evidence, and remove the temporary repository. |

## Trust Boundaries

- [DECISION] Host boundary: Environment variables and installed files are untrusted capability hints until active-session evidence confirms behavior.
- [DECISION] Shell boundary: Installer and validation commands use argument-array process execution and scoped project roots.
- [DECISION] Release boundary: Git tags, GitHub releases, npm publication, and credentials require explicit user-owned action; multi-package release versions stage and verify as a pair before `latest` promotion.
- [DECISION] Connector boundary: External writes remain delegated to host connectors with explicit scope.
- [DECISION] Provenance service boundary: redirects, embedded credentials, mixed-trust DNS sets, unsupported service contracts, malformed responses, and unavailable requested capabilities fail closed before output publication.
- [DECISION] Provenance credential boundary: `WATERMARKS_SERVICE_API_KEY` remains environment-only input and never enters request JSON, command arguments, Godpowers state, or generated reports.
- [DECISION] Provenance filesystem boundary: the bundled client pins input, parent, and destination identities, rejects unsafe links and concurrent changes, and retains a named recovery path when guarded restoration cannot complete.
- [DECISION] Harness path boundary: context files reject symlinks and retain pinned bytes, program-design approval binds to an exact path and digest, and handoff plus benchmark paths resolve within their declared roots before reads or writes.
- [DECISION] Harness content boundary: repository source and imports are inert measurement input, loadout events omit contents, and compact logs never add environment dumps or credentials.
