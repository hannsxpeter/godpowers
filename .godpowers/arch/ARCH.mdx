# Godpowers System Architecture

## System Context

- [DECISION] A developer invokes Godpowers inside an AI coding host, which loads installed skills and specialist agents from the host-specific runtime directory.
- [DECISION] Godpowers reads and writes project-local Pillars, `.godpowers` state, planning artifacts, source files, and verification evidence.
- [DECISION] GitHub Actions and npm are external release services reached only after explicit user authority and identity-bound release gates.

## Architecture Decision Records

### ADR-001: Keep workflow state on disk

- [DECISION] Context: AI coding sessions end, compact, and move between hosts.
- [DECISION] Decision: `.godpowers/state.json` is authoritative and generated views derive from it.
- [DECISION] Rationale: A new session can verify state without trusting conversation memory.
- [DECISION] Flip point: Replace JSON state only if a portable store offers atomic local reads, offline operation, and deterministic export with lower complexity.
- [DECISION] Consequence: State writers must refresh generated views and checkpoints.

### ADR-002: Keep runtime helpers dependency-light

- [DECISION] Context: The installer targets 15 AI coding runtimes and must work in unfamiliar repositories.
- [DECISION] Decision: Runtime helpers use Node.js built-ins and CommonJS, with no production dependency required by the core package.
- [DECISION] Rationale: The package avoids install-time dependency conflicts inside user projects.
- [DECISION] Flip point: Add a dependency only when a measured compatibility or correctness benefit exceeds package and supply-chain cost.
- [DECISION] Consequence: Parsers and filesystem helpers need focused local tests.

### ADR-003: Separate installed capability from active-session evidence

- [DECISION] Context: An agent file on disk proves installation but not that the current host session can spawn a fresh agent.
- [DECISION] Decision: Full host guarantees require an identified host plus explicit active-session spawn evidence.
- [DECISION] Rationale: The dashboard must never report `full on unknown`.
- [DECISION] Flip point: A host-native capability handshake may replace explicit evidence when it is stable and testable.
- [DECISION] Consequence: Some capable hosts report degraded until the active session confirms spawning.

### ADR-004: Keep authorized provenance cleaning in a lazy extension

- [DECISION] Context: provenance cleaning is optional, relies on a separately operated service, and does not belong in every Godpowers project run.
- [DECISION] Decision: ship `@godpowers/provenance-pack` with `/god-remove-ai-marks` and `god-ai-provenance-cleaner` instead of adding a core command.
- [DECISION] Rationale: the extension preserves the frozen core command surface, avoids root production dependencies, and activates only after explicit installation.
- [DECISION] Flip point: move the command into core only if provenance inspection becomes a required gate for most Godpowers workflows and can run without a second runtime or a silent external data path.
- [DECISION] Consequence: users install the pack and operate the upstream service separately.

### ADR-005: Reuse the upstream HTTP contract through a deterministic client

- [DECISION] Context: the selected upstream project owns the provenance-cleaning algorithms but its service responses, network destinations, and filesystem effects cross trust boundaries.
- [DECISION] Decision: ship a dependency-free Node.js client that validates service compatibility, pins approved addresses, rejects redirects, bounds and sanitizes responses, validates output bytes, and publishes through guarded atomic replacement.
- [DECISION] Rationale: deterministic enforcement closes network, response, and filesystem gaps that a prose-only agent contract cannot close while leaving cleaning algorithms upstream.
- [DECISION] Flip point: replace the bundled client only when the upstream publishes a dependency-equivalent signed client with the same network, response, and file-safety guarantees.
- [DECISION] Consequence: service outages disable the extension but do not affect the Godpowers core runtime.

### ADR-006: Require visible consent for remote content transfer

- [DECISION] Context: authorized source files can still contain personal, confidential, or proprietary data.
- [DECISION] Decision: loopback HTTP is the default; a non-loopback destination requires HTTPS and a grant matching its exact normalized origin, with a separate exact-origin grant for private network addresses.
- [DECISION] Rationale: the user sees and controls each external file transfer while remote retention remains disclosed as unknown unless policy evidence is available.
- [DECISION] Flip point: replace per-invocation consent only when a shared integrations contract provides durable destination grants with revocation and retention metadata.
- [DECISION] Consequence: remote service use has a deliberate confirmation step before source bytes enter a request payload.

### ADR-007: Gate bounded context and program shape before execution

- [DECISION] Context: prompt prose alone cannot prove that a specialist received the required project facts or that a larger implementation has an approved code shape.
- [DECISION] Decision: specialist context declarations validate to pinned bytes, and medium or large program-design approval comes from a hash-chained `user.resolve` event bound to the exact plan path and digest before spawn or Build closeout.
- [DECISION] Rationale: missing inputs, oversized required context, project-external plans, and unapproved code shape fail before implementation evidence can be accepted.
- [DECISION] Flip point: relax a validation rule only after measured false-block evidence identifies a narrower deterministic replacement.
- [DECISION] Consequence: every workflow specialist has a bounded contract, while larger changes carry explicit design and approval evidence.

### ADR-008: Keep handoffs and maintainability measures as derived projections

- [DECISION] Context: compact resume records and code-shape measures help later decisions but can drift if they become a competing workflow authority or an uncalibrated score gate.
- [DECISION] Decision: derive handoffs from current authoritative evidence, resolve conflicts in favor of state, and keep individual maintainability measures report-only for three release candidates.
- [DECISION] Rationale: projections can be regenerated without losing truth, and reviewers retain responsibility for interpreting whether a delta is material.
- [DECISION] Flip point: advisory maintainability thresholds may be considered after three release-candidate datasets, but state authority remains fixed by ADR-001.
- [DECISION] Consequence: slice transitions remain resumable and measurable without promoting one metric or summary to source-of-truth status.

### ADR-009: Keep prose-quality detection advisory and local

- [DECISION] Context: labeled Godpowers prose can still hide actors, mechanisms, evidence, effects, or reader actions behind polished wording.
- [DECISION] Decision: C-prose-lint stays inside the existing Artifact layer, treats input as inert text, returns bounded sanitized findings, and enters universal validation only as U-12 warnings.
- [DECISION] Rationale: local structured warnings support human review without automatic rewriting, a model call, persistence, or a new external trust boundary.
- [DECISION] Flip point: reconsider a rule's advisory severity only after two release candidates provide reviewed precision evidence and a maintainer-approved override design.
- [DECISION] Consequence: existing artifact errors keep their severity, while maintainers receive deterministic prose findings that cannot block a gate by themselves.

### ADR-010: Bind blast-radius conclusions to existing executed evidence

- [DECISION] Context: a Stage 2 reviewer can trace source and static impact candidates without proving the single condition that makes a cross-boundary change safe.
- [DECISION] Decision: Stage 2 names exactly one load-bearing safety fact, scans 10 boundary classes, grades evidence from level 1 through level 5, and resolves every level 4 or level 5 conclusion to one fresh successful record in the existing verification ledger.
- [DECISION] Decision: C-evidence-review-resolver binds the unchanged executed record to a digest-bearing `gate.pass`, validates the event chain and expected claim, exact command, canonical substep, result, and freshness, then returns only match booleans and bounded redacted metadata.
- [DECISION] Decision: levels 1 through 3 remain `UNPROVEN`; high-impact uncertainty fails Stage 2, lower-impact uncertainty warns with one exact next proof, and a change crossing at least 3 boundary classes or 2 high-impact classes receives 2 independent fresh-context passes.
- [DECISION] Rationale: reusing the ledger, event chain, and state rollup preserves one evidence authority and avoids a competing store, command, dependency, or state writer.
- [DECISION] Flip point: reconsider the wide-change threshold after two release candidates record trigger frequency and unique high-impact findings; reconsider resolver indexing only after a deterministic corpus benchmark demonstrates that linear local reads exceed the review latency envelope.
- [DECISION] Consequence: static impact, source tracing, and reviewer agreement remain candidate evidence, the resolver remains read-only and fail closed, and the trusted-workspace chain is integrity evidence rather than authentication against an actor who controls every local trusted file.

### ADR-011: Make engineering authority explicit and keep optional operations lazy

- [DECISION] Context: runtime verification, debugging, archaeology, decision recall, route invocation, issue triage, and setup assistance can appear complete while omitting the product boundary, learning evidence, source diversity, authority class, or human approval that makes the result safe.
- [DECISION] Decision: C-engineering-contracts adds bounded dependency-free validators to existing commands and event surfaces, every canonical route declares one deterministic invocation policy, and C-operations-pack remains a separately installed extension with no core command.
- [DECISION] Decision: durable decision records stay inside the existing hash-chained event stream, the read-only trace verifies one immutable snapshot, and secret-bearing fields, values, authorities, queries, and unsafe fragments fail before append or projection.
- [DECISION] Rationale: explicit machine-readable contracts make omissions observable while retaining one state authority, one event authority, the frozen 124-command surface, and approval-required handling for external or destructive actions.
- [DECISION] Flip point: promote an operations-pack capability into core only after measured use shows it is required by most project runs and a core route can preserve the same human approval boundary without adding external mutation authority.
- [DECISION] Consequence: existing commands become stricter where evidence or authority is required, optional operations stay lazy, and the root package keeps zero production dependencies.

### ADR-012: Keep adaptive run selection advisory within existing commands

- [DECISION] Context: the Godpowers front door can mistake a large-repository assessment for a whole-project objective or load a full workflow for a bounded edit before inspecting the requested outcome.
- [DECISION] Decision: the current host model classifies task, scope, risk, and uncertainty from the user request and bounded repository evidence, then calls `lib/command-families.selectRunApproach` within the existing Decision runtime to recommend direct, focused, or full work.
- [DECISION] Decision: ordinary questions and assessments finish in chat, `/god-fast` requires `mechanical: true` plus bounded scope, low risk, and low uncertainty, and a full recommendation retains `/god-mode`'s explicit-only invocation policy.
- [DECISION] Decision: named commands retain mandatory stages and execution authority; `/god-debug` returns an uncommitted fix to fresh Stage 1 specification review followed by fresh Stage 2 quality review before the authorized caller commits.
- [DECISION] Rationale: the existing command-family helper can validate categorical inputs and expose the existing invocation policy without another command, module, dependency, selector agent, selection artifact, or state writer.
- [DECISION] Flip point: revise the classification fields or mapping when one reproducible ordinary request selects an unsafe or unnecessarily broad command from correctly supplied categories; any replacement must retain named-command prerequisites, required review, and invocation authority.
- [DECISION] Consequence: the helper cannot prove that the host model assessed the repository correctly, so observed sensitive boundaries require high-risk treatment, absent scope or risk evidence remains unknown, and changed evidence triggers reassessment without repeating still-valid work.
- [DECISION] Consequence: model identity and repository size grant no gate bypass, conditional steps may be omitted only when their documented conditions are absent, and no total token-spend reduction is guaranteed.

## Critical Flows

### Authorized provenance inspection and cleaning

1. [DECISION] C-provenance-skill establishes authorization and delegates the selected path and mode to C-provenance-specialist without changing the source.
2. [DECISION] C-provenance-specialist invokes C-provenance-client, which validates the service origin, destination grants, resolved address set, service version, OpenAPI shape, and requested capabilities before reading source bytes into a request payload.
3. [DECISION] C-provenance-client pins the input, parent, and destination identities, then asks C-watermarks-remover-service to inspect before it requests cleaning.
4. [DECISION] C-provenance-client bounds and sanitizes the service response, validates canonical base64 plus the output format, and publishes to C-user-filesystem through guarded atomic replacement.
5. [DECISION] C-provenance-specialist reports deterministic removals, optional best-effort work, and unresolved risks separately without echoing service-controlled strings as instructions.

### Harness-quality build flow

1. [DECISION] C-context-loadout validates the chosen specialist's required files, optional files, inline task inputs, token cap, path identity, and pinned bytes before orchestration spawns it.
2. [DECISION] C-program-design validates scale and either a small-change skip rationale or complete code-shape evidence plus hash-bound approval before Build can close.
3. [DECISION] C-verification-runner executes checks in order, stops at the first failure in agent mode, and references complete retained evidence from a bounded summary.
4. [DECISION] C-maintainability-trajectory compares the pre-edit and post-verification snapshots, and the independent quality reviewer interprets every material deterioration.
5. [DECISION] C-slice-handoff writes a bounded projection for resume, with current state winning every conflict.
6. [DECISION] C-evolution-benchmark repeats behavior and maintainability evidence across six isolated checkpoint reveals and retains JSON plus Markdown summaries after temporary cleanup.

### Advisory prose-quality flow

1. [DECISION] The Artifact layer passes caller-owned Markdown or MDX text to C-prose-lint without granting filesystem, network, model, or mutation authority.
2. [DECISION] C-prose-lint masks frontmatter, fenced code, inline code, link destinations, and clearly quoted bad examples before matching high-confidence sentence patterns.
3. [DECISION] C-prose-lint returns ordered findings with bounded excerpts after terminal control bytes are removed.
4. [DECISION] The universal have-nots wrapper maps each finding to a U-12 warning, while the existing artifact linter preserves every blocking error and aggregate warning count.

### Blast-radius Stage 2 flow

1. [DECISION] The executor proposes one candidate safety fact, implicated boundary classes, and the smallest focused proof without grading its own work.
2. [DECISION] Stage 1 verifies specification, acceptance, traceability, and scope without deciding the blast-radius safety case.
3. [DECISION] Stage 2 independently verifies or replaces the candidate, records all 10 boundary classes, and calculates whether the change is bounded or wide.
4. [DECISION] A bounded change receives one fresh-context safety-case pass, while a wide change receives a second independent pass and a reconciliation that cannot convert agreement into proof.
5. [DECISION] C-evidence-review-resolver checks each level 4 or level 5 citation against one unique fresh successful ledger record and its digest-bound gate event, then returns a sanitized projection to the reviewer.
6. [DECISION] A confirmed blocking risk or high-impact Unproven Claim fails Stage 2; a lower-impact Unproven Claim remains visible with one exact next proof.

### Engineering-leverage flow

1. [DECISION] Product routing selects one of six verification forms, and C-engineering-contracts validates that form's material user paths, failure paths, and completion evidence before `/god-test-runtime` can report completion.
2. [DECISION] `/god-debug` requires an executed deterministic reproduction before hypothesis work, then rejects repeated tests or predictions that add no information.
3. [DECISION] Medium and large Build plans record callers, pressures, two alternative shapes, one selected shape, and a return-to-planning rule for repeated deviation.
4. [DECISION] `/god-archaeology --why` validates independent cited evidence for one exact target, while default archaeology remains unchanged.
5. [DECISION] Decision writers append validated `decision.recorded` events, and `/god-trace --decisions` projects only validated records from verified run snapshots.
6. [DECISION] Router and route-quality checks derive invocation authority from canonical route identity, while the optional operations pack waits for explicit human approval before tracker or setup actions.

### Adaptive run selection flow

1. [DECISION] The current host model preserves explicit commands, reads required Pillars and bounded evidence, and records the ordinary assessment in the current chat without a new persistent artifact.
2. [DECISION] The existing Decision runtime validates the task, scope, risk, and uncertainty categories and returns an approach, command or null, reason, useful components, recommendation-only authority, and the existing invocation policy.
3. [DECISION] A direct answer stops routing; a selected command keeps its prerequisites, verification, review, and authority while the model reuses valid evidence and omits only inapplicable conditional work.
4. [DECISION] Focused debugging returns the uncommitted fix through the existing two-stage review sequence before the caller commits under the user's existing authority.
5. [DECISION] New evidence can change the assessment and expand the selected work, but only the existing orchestrator and command contracts may write workflow state or accept completion evidence.

## Failure and Degradation

| Dependency or step | Timeout and retry stance | User-visible degraded state |
|---|---|---|
| Service health and contract | [DECISION] Use a 5 second connection deadline and 30 second total deadline, reject redirects, and retry no request; the health and contract reads are idempotent by canonical service origin plus requested version. | [DECISION] Report the service as unreachable or incompatible and write no output. |
| Inspect or clean request | [DECISION] Use one 60 second absolute operation deadline and never retry; inspection is read-only, but cleaning is not assumed idempotent without a service-issued operation key. | [DECISION] Preserve source and destination files and report that completion is unknown. |
| Optional pixel backend | [DECISION] Start only after explicit approval and a matching capability response, with no automatic fallback. | [DECISION] Name the unavailable or timed-out capability without claiming pixel removal. |
| Response validation | [DECISION] Reject malformed, oversized, unsupported, kind-mismatched, or noncanonical data without retry. | [DECISION] Keep all final paths unchanged and return a fixed response-contract failure. |
| Guarded publication | [DECISION] Reject parent or destination identity changes and attempt one local restoration when replacement publication fails. | [DECISION] Preserve the competing file, restore the prior destination when possible, and report any retained recovery path. |
| Context or plan validation | [DECISION] Complete each local validation within a 30 second harness deadline, reject missing, escaped, contradictory, oversized, or negatively approved evidence, and never retry; the read-only validation is idempotent by input-byte digest. | [DECISION] Return bounded findings and leave authoritative state unchanged. |

| Evidence review resolution | [DECISION] Read the existing ledger and event chain once per cited record, execute no stored command or output, and reject absent, duplicate, failed, mismatched, stale, unbound, digest-mismatched, or invalid-chain evidence without retry. | [DECISION] Return a bounded sanitized rejection projection, preserve the record and event files unchanged, and keep the safety claim `UNPROVEN`. |

## Trust Boundaries

- [DECISION] Host boundary: Environment variables and installed files are untrusted capability hints until active-session evidence confirms behavior.
- [DECISION] Shell boundary: Installer and validation commands use argument-array process execution and scoped project roots.
- [DECISION] Release boundary: Git tags, GitHub releases, npm publication, and credentials require explicit user-owned action; multi-package release versions stage and verify as a pair before `latest` promotion.
- [DECISION] Connector boundary: External writes remain delegated to host connectors with explicit scope.
- [DECISION] Provenance service boundary: redirects, embedded credentials, mixed-trust DNS sets, unsupported service contracts, malformed responses, and unavailable requested capabilities fail closed before output publication.
- [DECISION] Provenance credential boundary: `WATERMARKS_SERVICE_API_KEY` remains environment-only input and never enters request JSON, command arguments, Godpowers state, or generated reports.
- [DECISION] Provenance filesystem boundary: the bundled client pins input, parent, and destination identities, rejects unsafe links and concurrent changes, and retains a named recovery path when guarded restoration cannot complete.
- [DECISION] Harness path boundary: context files reject symlinks and retain pinned bytes, program-design approval binds to an exact path and digest, and handoff plus benchmark paths resolve within their declared roots before reads or writes.
- [DECISION] Harness content boundary: repository source and imports are inert measurement input, loadout events omit contents, and compact logs never add environment dumps or credentials.
- [DECISION] Artifact-quality boundary: prose input remains inert caller-owned text, C-prose-lint performs no I/O, terminal control bytes are removed from excerpts, findings are capped at 160 characters, and U-12 remains advisory; this local path adds no external trust boundary.
- [DECISION] Blast-radius evidence boundary: `lib/evidence.js` reads the existing local ledger and hash-chained events, compares caller-supplied expectations, and returns a sanitized projection without executing stored content or acquiring write authority.
- [DECISION] Trusted-workspace boundary: digest and chain validation detects accidental or inconsistent local mutation but does not authenticate against an actor who can rewrite every trusted project file and recompute the complete chain; repository access controls, signed commits, CI identity, and publish provenance cover that stronger threat model.
- [DECISION] Invocation boundary: canonical route filenames own command identity, duplicate or spoofed route metadata fails closed, and approval-required commands never inherit weaker authority from self-declared metadata.
- [DECISION] Operations extension boundary: issue triage is advisory until separate maintainer approvals, generated setup scripts are statically checked rather than executed end to end, secrets use hidden input or stdin, and exact repository authority is verified before GitHub mutation.

- [DECISION] Adaptive selection boundary: host-supplied categories are an assessment rather than proof, and the returned recommendation cannot grant execution authority, bypass required stages, or mark skipped work complete.
